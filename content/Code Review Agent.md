**为什么要设计Code Review Agent？**

现有的AI编码在复杂链路修改中容易出现幻觉，导致Reviewer难以快速理解真实影响范围。现有的AI编码工具在简单任务上表现很好，但是在涉及多级读写链路、跨函数调用、跨模块依赖的复杂任务中，容易出现理解不完整、推理跳步或者局部正确但整体失真的问题。这种问题通常体现在这几个方面：

- 开发者需要在大量的源码细节中手动还原真实的调用链。
- 在大量改动的情况下，Reviewer很难在短时间内判断改动是否影响了更高层的业务链路或架构路径。
- 代码diff主要展示文本改动，但不能直接表达类似于”这次改动改变了哪条调用路径“
- 当调用关系较深、分支较多时，单纯依赖人工或者AI解释都容易丢上下文。

我认为根本的问题不只是”代码变多了“，而是缺少一种介于代码细节和高层架构之间的中间表示。开发者在review时需要的并不是所有实现细节的逐行展开，而是一个能够表达调用关系、结构归属和影响传播路径的抽象视图。没有这层抽象，复杂的改动要么只能依靠人工在源码中来回跳转，要么只能依靠AI给出的高层总结，而两种都难以稳定支撑复杂code review

**语法解析与语义绑定分层**

在技术选型上，需要明确区分“语法事实提取”和“语义关系解析”这两个层次。`tree-sitter` 的能力边界非常清晰：它擅长高性能地构建语法树，并通过 query 提取结构化代码事实，例如函数定义、方法定义、import、call expression、selector expression、type declaration 等。这使它非常适合作为底层的通用解析器，用于抽取 `file / function / import / call-site / type` 等语言无关或弱语义的代码事实。

但 `tree-sitter` 并不负责名字解析、符号绑定和类型推断。它可以告诉我们“这里出现了一个调用表达式”或“这里存在一个 `svc.run()` 形式的 selector call”，但它不能直接回答“这个 `svc` 的静态类型是什么”、“这个 `run` 最终绑定到哪个 method symbol”、“这个 identifier 是否引用了当前 package、外部 package 还是 interface dispatch”。

这些问题在 Go 中属于另一层能力。Go 官方工具链本身也体现了这种分工：`go/types` 负责 identifier 到 symbol 的映射、类型检查和类型推断，`go/packages` 负责将 package、syntax、`TypesInfo` 等上下文一起加载出来。因此，从架构上看，AST 解析和高精度调用绑定本来就不是同一层问题。

基于这一点，本项目在设计上应采用分层策略：底层使用 `tree-sitter` 或语言原生 AST 提取代码事实；中间层通过 resolver 对这些事实进行名字解析和关系补全；在 Go 语言上，若需要更高精度的 `CALLS`，则应逐步引入 `go/types` / `go/packages` 作为语义增强层，而不是把这部分能力错误地寄托在 AST 或 query 层上。这样做的好处是边界清晰，也更利于后续扩展到多语言：语法层保持统一，语义层按语言逐步增强。
